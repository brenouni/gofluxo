SPEC-64 — Identificação do operador e origem da auditoria

Decisão do responsável: 19/10/2026.

Novos eventos HTTP devem conter o identificador do operador e, quando conhecido no servidor, snapshot de nome/login do usuário que executou a operação, data/hora UTC, IP, navegador, sistema operacional, classe do dispositivo e agente do navegador. Incluir autenticações já auditadas, inclusive Login.Succeeded. Falha de login com identidade desconhecida não deve atribuir um operador fictício nem armazenar o login digitado por um desconhecido. Não copiar senhas, cookies, tokens ou o corpo da requisição.

A identidade é resolvida pelo identificador auditado no banco, nunca pelo nome enviado pelo cliente. IP vem de RemoteIpAddress após os proxies confiáveis existentes, sem interpretar X-Forwarded-For diretamente. Navegador e dispositivo são inferidos do User-Agent, limitado a 512 caracteres e sem caracteres de controle; são informações declaradas pelo cliente, não prova de identidade física. Nome/login têm os limites do cadastro.

Lista apresenta operador, login, horário de Brasília, IP, navegador e dispositivo, além de módulo/operação/resultado. Detalhes mostram UTC, sistema operacional, agente e localização/fonte. A busca existente sobre o JSON permite encontrar novos campos. Novas colunas de contexto não anunciam ordenação SQL ainda não implementada.

Localização física: IP não informa endereço exato. Sem base GeoIP ou outra fonte confiável, exibir Não determinada. O responsável escolheu cidade/região aproximada por IP. Implementar DB-IP Lite MMDB local, com leitor único mapeado em memória, suporte IPv4/IPv6 e atribuição CC BY 4.0. Não enviar IPs a serviços externos nem solicitar GPS. Base ausente, inválida, IP privado ou sem cobertura retorna localização não determinada, sem bloquear o evento. Base local de outubro/2026 instalada e checksum oficial conferido; cloud exige atualização específica. Não persistir coordenadas ou endereço exato.

Metadados são opcionais no evento V1 e armazenados no JSON já existente, sem migração. O campo request nulo é omitido para preservar serialização/hash e reprocessamento de eventos históricos. Não completar retroativamente registros antigos com dados atuais. Eventos de processos sem HTTP permanecem sem contexto de navegador.

Manter autorização/escopo existentes de auditoria, deduplicação, validação dos limites, outbox e integridade. Implantar consumidor compatível antes ou junto da API que emite o novo campo; consumidores antigos rejeitam propriedades desconhecidas.
